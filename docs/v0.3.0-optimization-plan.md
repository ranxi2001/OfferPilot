# OfferPilot v0.3.0 优化方案

> 状态：Planned
> 基线：v0.2.0
> 目标：把“核心链路可用”升级为“真实面试质量可量化、失败可恢复、部署可审计”

## 1. 发布目标

v0.3.0 不以继续增加页面或 Agent 数量为主，而是收紧三个结果：

1. 给定真实 JD 和简历，问题必须与岗位、项目和上一轮回答直接相关，并形成
   可解释的深挖路径。
2. 超时、刷新、重复提交和进程重启不能造成重复问题、重复计分或会话丢失。
3. 每次发布必须用固定数据集量化问题质量、事实性、隐私、延迟和恢复能力，
   不能只依赖“页面能打开”和模型偶然返回成功。

模型私有原始思维链不属于产品输出。用户看到的是完整、连续、可持久化的执行
轨迹、证据引用和决策摘要。

## 2. 优先级方案

### P0：没有这些能力不发布

| 优化项 | 当前缺口 | 实施落点 | v0.3.0 验收标准 |
|---|---|---|---|
| 真实模型面试 Eval Harness | 当前测试能验证协议和状态，但无法证明问题“问得好” | 新增 `backend/evals/`，拆分确定性离线 corpus、手动/定时真实 provider runs 和人工双盲评审；固定 model、Prompt、schema、rubric、knowledge generation、seed 和结果清单 | 30 个互不重复的离线案例各运行 1 次；12 个真实 provider 案例各重复 3 次，共 36 场，覆盖 4 个方向和 3 个职级，其中至少 4 个为真实 JD + 简历混合面试；从候选版本和基线中抽取至少 60 组配对结果，由 2 名评审独立双盲评分，分差超过 1 分时由第 3 人裁决；相关性、深挖度、可回答性均分不低于 4/5，重复题和参考答案泄漏为 0 |
| Typed Profile 提取 | 当前 JD/简历 Profile 仍主要依赖分句、关键词和固定技能表，复杂材料会丢失职责边界、职级和指标关系 | 将 `interview/sources.go` 的启发式提取拆为带 schema 的 `ProfileExtractor`，新增 `backend/internal/profile` 和受约束的 profile agent；所有字段保留原文 EvidenceRef | 至少 50 对按材料来源去重的 JD/简历由 2 名标注者独立标注并裁决分歧，其中至少 20 对在开发前冻结为 held-out test；must-have、项目、个人职责和指标抽取的 micro/macro F1 均不低于 0.90；引用定位有效率 100%；无引用推断不得进入事实字段 |
| 按覆盖点动态检索并严格绑定证据 | 当前开场只按整份材料做一次 BM25 top-K；`sources.go` 会把相同的头部知识锚点附给多个 JD 点，`service.go` 还可能补入会话最前面的知识引用，导致后续题目与参考证据错配 | 重构 `backend/internal/knowledge/interview_retriever.go`、`interview/sources.go` 和 `interview/service.go`；每个 coverage point 以岗位要求、当前问题和上一轮缺口重新检索，只允许生成题使用该次 evidence bundle | 至少 100 个双标注检索 query 的冻结集合达到 `Recall@5 >= 0.85`、`nDCG@5 >= 0.80`；每道知识题的引用都与 coverage point 同主题，跨主题头部 anchor 注入为 0；人工抽检 30 题的证据相关性均分不低于 4/5 |
| Answer 幂等与追加事件账本 | 当前 SQLite snapshot 有 CAS，但客户端重试缺少稳定 answer ID，无法按事件游标重放 | 扩展 `types.go`、`service.go`、`sqlite_store.go` 和 migration；引入 durable command/run 状态、`answer_id`、`session_seq`、`model_invocations(request_hash,status)`、checkpoint、run lease、outbox、唯一约束和 append-only events | 幂等作用域固定为 `(principal_id, session_id, route, client_answer_id)` 并保存 payload hash；同 key 同 payload 并发提交 20 次只产生 1 个 Assessment、turn 和可见问题并返回原 run/result；同 key 不同 payload、或已接受问题再次使用不同 answer ID 均返回 `409`；失败的 provider 工作恢复同一个 run/answer，不新建提交。外部 provider 调用只保证可追踪的 at-least-once，不虚构 exactly-once |
| 断线恢复与轨迹重放 | NDJSON 绑定请求上下文，网络断开会取消 run；刷新后没有服务端恢复入口，UI 状态直接丢失 | 命令先返回 `202 + runId + eventCursor`；持久 SSE 支持 `Last-Event-ID` 且不绑定浏览器断开；新增 session snapshot GET；浏览器只保存 `interviewId/clientAnswerId/lastSequence` | 刷新、断网 30 秒和服务重启后，已完成步骤不丢失、不倒退、不重复；网络断开不取消服务端 run；失败步骤能从同一问题重试 |
| 模型延迟与失败预算 | 真实验收中的 stream 请求耗时约 8.4 至 170.8 秒，但日志没有 action/stage 标签，无法可靠区分 start、answer 和 report | 为 `harness` 增加分阶段 deadline、action/stage/provider request ID、retry、repair、token 和耗时指标；保持“无有效 Assessment 不计分” | 在批准的参考 provider/model、单并发、暖进程环境中，首个轨迹事件 P95 小于 1 秒、Harness 自身开销 P95 小于 100 ms、start/answer/report 端到端 P95 分别不超过 90/150/90 秒、超时率低于 2%、repair 率低于 10%；deadline 触发后 2 秒内返回可重试错误且答案草稿仍在 |
| 可操作 readiness | 当前 `/health/ready` 只验证模型配置和 Harness 初始化，不能发现数据库只读、migration 落后、知识 generation 不一致或 run worker 停摆 | 新增分组件 readiness probe；以回滚事务验证 SQLite 可写，核对目标 migration version、active knowledge generation/manifest hash、run coordinator lease/heartbeat 和 outbox dispatcher lag；provider 实时探测独立展示 | 任一关键组件不满足时 10 秒内返回 `503` 和稳定错误码，绝不继续报告 ready；故障恢复后 30 秒内自动转绿；`/health/live` 保持独立；Compose 和故障注入测试覆盖数据库只读、旧 schema、索引错代、worker 停止及 outbox 堆积 |
| 隐私与 Prompt Injection 回归 | 已有确定性泄漏测试，但样本规模和变形覆盖有限 | 扩展 `privacy_contract_test.go`，增加带固定 seed 的 fuzz/property tests；覆盖 Unicode、标点、跨 anchor、编码和间接指令，并维护公开概念负样本集 | 10,000 个可复现自动变形样本中私有参考内容泄漏为 0；固定负样本的公开概念误伤率低于 1%；轨迹不包含 Prompt、JD/简历正文或答案正文 |

### P1：v0.3.0 承诺范围，同样阻断 GA

| 优化项 | 当前缺口 | 实施落点 | v0.3.0 验收标准 |
|---|---|---|---|
| 题目质量与 Claim Ledger | 当前有 claim checks，但没有独立、可追踪的完整声明账本 | 在 `backend/internal/interview` 新增 Claim 聚合与状态迁移；Planner 优先处理高价值未验证声明；Reporter 只汇总已提交证据 | 选中的高优先级项目至少覆盖职责、规模、决策、指标、故障或取舍中的 4 个轴；未抽查项目明确标记为未评估；矛盾声明必须触发核验或出现在报告风险中 |
| 文档摄取迁入 Go | PDF/DOCX/URL 提取仍由 Next.js BFF 承担，后端迁移未闭合 | 新增 Go document port/adapter 和受限 URL fetcher；Next.js 仅做同源代理与上传 UI | 固定语料中 PDF/DOCX/TXT/MD/TeX 提取结果与基线一致；大小、超时、重定向、DNS rebinding、私网访问测试全部通过 |
| Go 统一业务分析与状态 | `resume` 和 `match` 仍使用 Next.js 正则评分，`diagnosis` 使用进程内数组，chat 仍可启用 mock，导致页面间 Profile 和状态不一致 | Go 新增 `documents`、`profiles`、`matching`、`diagnosis` application/API；所有业务状态落 SQLite；Next.js 路由改为认证、限流和代理 | `web/src/app/api` 不再包含业务评分规则、模型 mock 或可变业务状态；上传、Profile、匹配、诊断和面试共用 Go 证据模型，Go/Node 任一重启不丢业务状态 |
| 混合检索与重排 | 在 P0 完成逐覆盖点证据绑定后，BM25 对缩写、同义表达和复杂 JD 的召回仍有限 | 在 `backend/internal/knowledge` 增加 embedding adapter、hybrid fusion 和可选 reranker；保存 index version、manifest hash | 同一冻结检索集的 nDCG@5 不低于 0.80 且相比 v0.2.0 BM25 提升至少 10%，`Recall@5` 不低于 P0 门槛，精确标题查询不回退；无 embedding 时可确定性降级到 BM25 |
| 面试控制与错误 UX | 用户缺少明确的暂停、恢复、重试和材料纠正闭环 | 扩展 `InterviewView.tsx`、材料预览和报告页；提供暂停/恢复、失败重试、Profile 确认及覆盖进度 | 移动端和桌面端均能完成上传到报告；错误状态给出可执行操作；任何动态文本不遮挡控件，键盘操作和焦点顺序通过检查 |
| 可观测性和成本 | 当前日志与 trace 能定位单次失败，但缺少聚合指标和发布对比 | 为 HTTP、Harness、模型、检索和 SQLite 增加 OpenTelemetry 或等价指标；只使用哈希会话 ID | 能按角色查看成功率、P50/P95 延迟、repair 率、token/成本、恢复次数和泄漏拦截数；日志中不出现材料正文 |

### P2：默认进入 v0.3.x/v0.4，仅在 Alpha 前锁定后才进入 v0.3.0

| 优化项 | 实施方向 | 验收标准 |
|---|---|---|
| Go 多供应商路由 | 将 Anthropic/DeepSeek 等适配器迁入 Go，按角色配置模型、预算和熔断策略 | 切换 provider 不改变 InterviewService 契约；故障供应商不会拖垮其他角色 |
| 语音面试稳态化 | 增加长音频分段、取消、上传进度和转写置信提示 | 10 分钟音频可取消、可重试；离开页面后麦克风和 AudioContext 均释放 |
| 会话生命周期 | 增加会话列表、显式删除和数据保留策略 | 用户能查看、恢复、导出和删除会话；删除操作有审计记录且不可误删其他会话 |

## 3. 里程碑

### v0.3.0-alpha.1：质量基线和故障语义

- 建立 30 个真实场景 Eval 数据集和自动评分汇总。
- 完成 durable command/run、model invocation、checkpoint、lease、outbox、answer ID、
  事件序号、唯一约束和迁移。
- 将真实供应商冒烟测试接入手动发布门禁。
- 扩充隐私 fuzz 与 Prompt Injection 测试。

退出条件：同一答案不会重复计分；固定样本没有泄漏和重复题；失败可重试。

### v0.3.0-beta.1：迁移闭合和用户恢复

- 文档提取、Profile、匹配、诊断状态与 URL 安全策略迁入 Go。
- 完成事件游标、刷新恢复、暂停和继续。
- 接入 Claim Ledger 与新的项目深挖策略。
- 上线混合检索实验开关和离线对比。

退出条件：Next.js 不包含业务评分规则、模型 mock 或可变领域状态；重启后能从最后
已提交事件继续。

### v0.3.0-rc.1：指标、性能和发布演练

- 完成延迟、成本、repair 和错误率仪表。
- 执行 SQLite 迁移、备份、回滚和旧会话兼容演练。
- 完成桌面与移动端真实浏览器验收。
- 冻结 schema、Prompt、Policy 和 Eval 数据集版本。

退出条件：所有发布门禁有留档结果；RC 在 48 小时内至少完成 20 场会话，其中
真实 provider 不少于 8 场，并完成至少 5 个并发会话；provider timeout、SQLite
busy、worker kill、SSE 断线和 API 重启故障注入各执行至少 1 次，数据一致性故障为 0。

### v0.3.0 GA：受控切流

- 冻结 feature flag，备份并验证迁移前 SQLite，记录 rollback checkpoint。
- 先灰度 Go 全链路；旧 TypeScript 后端停止接收新会话，但最后一个可回滚 artifact
  和旧库只读副本至少保留一个稳定版本窗口。确认不存在 TS-owned 活跃会话且恢复
  演练通过后，才移除生产镜像依赖和旧库副本。
- 使用固定 Changelog 创建 annotated tag 和 Release，并附迁移、回滚与 Eval 结果。

退出条件：P0 与 P1 全部完成，迁移备份可恢复，灰度指标不低于 RC 基线。

## 4. 发布门禁

v0.3.0 标签只能在以下条件全部满足后创建：

- `go test ./... -count=1` 和 `go vet ./...` 通过。
- 根项目 TypeScript 类型检查、unit/e2e 测试和 Web 生产构建通过。
- API/Web Docker 镜像构建通过，Compose readiness 通过。
- 30 个离线 Eval、12 个真实 provider 案例各 3 次运行和 60 组双盲样本均达到
  版本化质量阈值；真实 provider 集中至少 4 场使用真实 JD + 简历混合输入。
- 幂等并发、崩溃恢复、旧数据库迁移和事件重放测试通过。
- DB 可写、migration、知识 generation、run coordinator/worker 和 outbox readiness
  门禁及故障注入全部通过。
- P1 的 Go 业务迁移、Claim Ledger、错误 UX 和完整可观测性验收全部通过。
- 隐私、SSRF、Prompt Injection 和缓存报告投影测试通过。
- RC soak 满足真实 provider、并发、故障注入和零一致性故障要求。
- 发布说明列出 schema、migration、配置变化、已知限制和回滚步骤。

## 5. 明确不做

- 不展示模型私有原始思维链，只展示安全、可验证的执行事实和决策摘要。
- 不让模型直接执行 SQL、任意文件读写或不受限 URL 请求。
- 不把候选人自述标记成外部已核实事实。
- 不在没有容量数据前拆成微服务或引入分布式工作流平台。
- 不用静态兜底分数掩盖模型故障。
